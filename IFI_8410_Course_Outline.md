# Introduction to Python for Data Analytics — Course Outline
### 14 sessions · individual work only · 20% class activities / 80% CI-graded homework

## Catalog Alignment (v2 update)

This revision aligns the course with the official catalog description — which matches Georgia State's **IFI 8410, Introduction to Programming & Predictive Analytics for Business** (the "Citizen Data Scientist" track course that leads directly into **IFI 8420, Machine Learning and Deep Learning for Business**). Two changes ripple through the whole outline:

1. **Every coding example is now a business decision, not an abstract exercise.** The catalog examples — customer churn, customer segmentation, market-demand forecasting, and stock-price forecasting — are used as the running vignettes for the ML, simulation, and several earlier sessions, rather than generic textbook problems.
2. **Structured and unstructured data are used throughout, not just once.** Since the audience is the Citizen Data Scientist cohort (business/non-STEM backgrounds, communication-forward), a lightweight unstructured-data thread (customer reviews / text data) is woven in starting Session 2 and fused with structured data later, instead of being a single isolated "NLP week."

The CS-foundations material (algorithms, data structures, Section 6's comprehension-verification approach) stays, but every example below is now grounded in a business use case so it also sets up the modeling concepts IFI 8420 builds on next.

## Assumptions
- 14 weekly sessions, 2 hours 30 minutes each with a 10-minute break.
- No prior programming experience assumed; Jupyter is the on-ramp, but every homework after Session 4 requires a proper `.py` module/script, not just notebook cells.
- Git use is intentionally light in class — just enough to clone, edit, commit, and push an assignment so the CI/CD pipeline can grade it. Session 3 teaches exactly that minimal loop plus basic Unix navigation; deeper git/CLI/SSH material (branching, merge conflicts, permissions, pipes, ssh/scp, reading pipeline logs in depth) lives in supplementary self-paced class materials, not live lecture time.
- Students all work on the same shared JupyterHub server, which also lets you pre-install a custom course package that wraps embedding-model inference and any hosted-API calls behind simple function calls — students never manage model downloads or API keys directly.
- Students submit to individual repositories (GitLab, matching your existing class-space setup), and each push triggers a CI/CD pipeline that runs the autograder.
- No exams; "class activities" (20%) means short quizzes, live coding checks, and in-class exercises; "homework" (80%) means CI/CD-graded programming assignments, resubmittable until the deadline.
- AI-usage honesty logs are required but never scored by *how much* AI was used — grading instead leans on comprehension checks (explain-it-back write-ups, live code-reading quizzes, occasional oral walkthroughs) so students are rewarded for understanding their own submission, not for minimizing AI use.

## 1. Design Philosophy

**Notebooks → functions → programs.** Every unit starts in Jupyter for exploration, but the graded artifact for each homework (starting Session 4) is a set of well-documented functions in a `.py` module, imported and exercised by tests — this is what forces the "proper Python" habit rather than notebook spaghetti.

**Tools before theory, theory before algorithms.** Unix and git share a single Session 3, but deliberately taught *light*: just enough of the shell to navigate and run a script, and just enough git (`clone`/`add`/`commit`/`push`) to get a homework through the CI/CD pipeline. Git here is a submission mechanic, not a concept to master in class — deeper CLI/git/SSH material (permissions, pipes, branching, conflict resolution, log-reading) is handed out as supplementary self-paced materials students can work through on their own time, which also keeps the live session light rather than overloaded.

**NLP threads from rule-based to statistical to language models.** Rather than saving all text-processing concepts for one week, classical/rule-based NLP is introduced early as a side effect of the Python concept already being taught: regex-based tokenization and lightweight pattern-based NER pair with Session 2's string work; dictionary/lexicon-based stemming, lemmatization, and POS tagging pair with Session 6's dict/set work; and WordNet-based synonym/hypernym traversal plus a hash-set-backed name gazetteer pair naturally with Session 9's graph and hashing content. Session 13 then completes the arc with the statistical and learned side of NLP — TF-IDF, embeddings, and language models — so students see rule-based and learned approaches applied to the same underlying problem (finding related text) instead of meeting NLP cold in Week 13.

**Stats/ML/simulation/algorithms as "side effects."** Rather than separate deep-dive units, each of these is attached to the Python concept being taught that week, e.g., hashing is taught the same week students learn dictionaries; shortest path is taught with graphs as a data structure; a Monte Carlo simulation is the vehicle for teaching randomness and functions together. This keeps the course a *programming* course with data-science flavor, not a compressed stats/ML course.

**Every example is a business decision.** Per the catalog, students should learn to "identify the appropriate methods to collect, analyze, and visualize data and utilize data in decision making." So the recurring cast of examples across the semester is: predicting **customer churn**, **customer segmentation**, **market-demand forecasting**, and **stock-price forecasting** — the same four scenarios named in the catalog, revisited with more sophisticated tools as the semester progresses (word counts on reviews in Week 2 → churn classification in Week 12 → similarity search over reviews in Week 13 → forecasting simulation in Week 14). Both **structured data** (transaction/customer tables) and **unstructured data** (customer reviews, text) appear from early on and are eventually combined, matching the catalog's "both structured and unstructured data will be used throughout the course."

**Algorithms get their own two sessions back.** Search/sort (Session 8) and hashing/graphs (Session 9) are split back into two full sessions rather than one condensed survey, so each gets proper build-and-benchmark depth instead of being rushed. The slot for this came from merging Unix+git into Session 3 above — a straight swap, not a net reduction in coverage. Session 9 also picks up the WordNet-graph and hash-set-gazetteer NLP side examples described above. Session 13 (Text Processing, Embeddings & Language Models, right after the ML week) still expands the unstructured-data thread from Week 2 into embeddings, nearest-neighbor search, FAISS, and language models, and remains a direct on-ramp to IFI 8420.

**Sets up IFI 8420.** Since this course is the direct prerequisite to a course on the *strategic and business implications* of ML/AI, the goal here is comfort with the mechanics (loading data, fitting a simple model, reading an evaluation metric, and now, representing text as vectors) — not depth. Sessions 12-14 close with short "what would a business actually do with this, and what could go wrong" discussion prompts that preview the questions IFI 8420 will take much further.

**AI tools are supervised, not scored.** Given your goal — students should learn to use AI tools well, not lean on them to skip learning — and given that AI use is genuinely hard to quantify, the course asks for honest disclosure (a short usage log, graded only on completion) rather than trying to penalize AI use itself. The real check is whether students understand what they submitted: explain-it-back write-ups, live code-reading quizzes, and occasional oral walkthroughs test comprehension directly, independent of how the code was produced. AI usage is also taught explicitly as a skill (Session 7). Section 6 below details the specific mechanisms.

## 2. Grading Structure

| Component | Weight | Composition |
|---|---|---|
| Class activities | 20% | In-class quizzes (concept checks, code-reading, "predict the output"), live coding exercises, occasional short git/unix labs |
| Homework (CI/CD-graded) | 80% | ~12–13 individual programming assignments, each graded on: automated correctness tests, code quality/style checks, student-authored tests, and completion of a short honesty/AI-usage log |

Suggested split **within** each homework's 80%-bucket score (adjust per assignment):
- 65% automated correctness (hidden + visible pytest tests run in the pipeline)
- 15% code quality (linting + docstrings/naming, optionally reviewed by an LLM-based rubric pass)
- 10% student-authored tests (scored on coverage/thoughtfulness, not just presence)
- 10% completion credit for the 3–5 sentence AI-usage/process reflection — pass/fail on honesty and completeness only. A student who used AI heavily and says so clearly gets full credit here, same as a student who used none at all; AI *amount* is never scored, up or down. Comprehension is checked separately, through the mechanisms in Section 6, not by scaling this reflection to how much AI was used.

Students may re-trigger the pipeline as many times as they want before the deadline; only the last (or best, your call) run before the deadline counts.

## 3. Autograding Infrastructure

Standardize on one submission pattern from day one: a stub module (`solution.py` or similar) with function signatures and docstrings, a `tests/` folder with a pytest suite, and a `.gitlab-ci.yml` pipeline that installs dependencies and runs `pytest` on every push. This mirrors how GitHub Classroom's built-in Python autograding preset works (setup command → `pytest` → points per passing test) and translates directly to GitLab CI/CD runners you already operate ([GitHub Docs](https://docs.github.com/en/education/manage-coursework-with-github-classroom/teach-with-github-classroom/use-autograding), [GitHub Classroom Python Grader](https://github.com/classroom-resources/autograding-python-grader/blob/main/README.md)).

Two additions worth building in, since you already run this pattern for your other course:
- **A second CI stage that pipes the diff through your Ollama-backed reviewer** for style/clarity feedback (docstrings, naming, obvious anti-patterns) — the same code-review workflow you use for project grading elsewhere, just scoring the 15–20% quality bucket here instead of pass/fail.
- **A per-student personalization step**: seed a small set of parameters or a data sample per student (e.g., derived from a hash of their student ID) so hidden tests check against values that differ from student to student. This alone kills a large share of copy-paste-from-a-classmate-or-a-shared-AI-answer submissions without adding any manual grading (this pattern is used at scale in production autograding setups — see [this 300-student GitHub Classroom case study](https://medium.com/@ayeshashafique123/scaling-autograding-for-300-students-with-github-classroom-and-custom-workflows-9c5f4111fa6d)).
- **A shared course package pre-installed on the JupyterHub server.** Since everyone works on the same server, you can install one internal package (e.g., `course_nlp`) that wraps model-inference calls — a local embedding model and/or a hosted language-model API — behind simple functions like `embed(text)` or `ask_llm(prompt)`. Students never touch model downloads or API keys, you control cost and rate limits centrally, and it resolves the Session 13 embedding-model question directly.

For the first couple of weeks, before students can write full modules, you can still autograde notebook exercises directly with a lightweight tool like [Otter Grader](https://otter-grader.readthedocs.io/) or [nbgrader](https://nbgrader.readthedocs.io/en/latest/command_line_tools/nbgrader-autograde.html) if you'd rather not build throwaway pytest stubs for trivial early exercises — but I'd recommend switching to the pytest-in-CI pattern no later than Session 4 (Functions & Program Design) so students internalize one workflow for the rest of the course.

## 5. Homework Assignment Suggestions in Detail

Each assignment below follows the same submission shape (stub module + tests + CI/CD pipeline) so students never have to relearn logistics, only new content.

1. **Warm-up functions (Wk 1)** — Fill in 4–5 tiny stub functions (unit conversion, simple math). Low stakes; purpose is to get everyone through their first green pipeline run.
2. **Customer-review word-frequency/keyword-flagging + regex fields (Wk 2)** — Given a small set of raw customer reviews (unstructured text), count word frequencies and flag reviews containing negative keywords (e.g., "cancel," "refund," "disappointed"), then use the `re` module to pull out structured fields (order numbers, dates, product codes) as a first taste of pattern-based NER. This is the course's first unstructured-data example and a preview of the churn signal used again in HW11, HW12, and HW13. Introduces string manipulation without requiring formal functions yet if you want to hold that for Wk 4.
3. **Shell + git submission (Wk 3)** — A Python script that reads from stdin/a file path passed as a CLI arg and writes results to another file, graded partly by running it through a small shell test harness. Submitted through the standard clone/add/commit/push loop; grading focuses on the script itself, not on git process depth (branching/conflict resolution is left for the supplementary git materials, not required here).
4. **Function library refactor (Wk 4)** — Take a working-but-ugly script and refactor into 4–6 documented functions with type hints; write tests for at least two functions yourself (graded for coverage/thoughtfulness, not just presence).
5. **Standalone CLI tool (Wk 5)** — A log or CSV analyzer with `argparse`, proper error handling, and a `--help` message; this is the first "would actually be useful" program.
6. **Data structure benchmark + dictionary-based stemmer/lemmatizer (Wk 6)** — Implement the same lookup/dedup feature with a list and with a set/dict, then measure and explain the timing difference in a short written note; separately, build a small stemming function (suffix-stripping rules) and a lemmatizer/POS tagger backed by a lookup dictionary, and apply both to the HW2 review text.
7. **Tests-first + AI reflection (Wk 7)** — Students write the test suite before the implementation, then may use an AI assistant to help implement, but must submit a short log: prompts used, what was wrong or needed correction, and one thing they learned about the tool's limits. This is graded for completeness/honesty of the reflection, not for whether AI was used.
8. **Search & sort benchmark (Wk 8)** — Implement linear/binary search and one or two sort algorithms and benchmark against Python's built-ins on a per-student seeded **transaction/order dataset** ("why does lookup speed matter when a retailer has millions of orders"); short written note interpreting the timing results.
9. **Hash lookup + shortest path + WordNet bonus (Wk 9)** — (a) build a hash table (or use a dict deliberately and explain the collision-handling underneath) for fast customer-ID/product-SKU lookup, and reuse the same hash-set pattern as a small NER gazetteer over the review text; (b) implement BFS or Dijkstra to find the shortest/cheapest route through a small provided **distribution or delivery network** (warehouses/stores as nodes, travel time or cost as edge weight — a supply-chain-analytics staple; a flight-route network works too if you'd rather use that framing); (c, optional bonus) traverse WordNet with NLTK to find related terms for a product category, framed as a graph-traversal exercise on a real-world graph.
10. **Demand/sales descriptive-stats mini-analysis (Wk 10)** — Compute descriptive stats and basic probability estimates (e.g., via simulation or `numpy.random`) on a personalized **sales-by-region-or-product sample**; short written interpretation required, framed as "what would you tell a manager about this month's demand pattern."
11. **A/B test + structured/unstructured fusion report (Wk 11)** — Clean and explore a **customer dataset** unique to each student, join it with a review-sentiment/keyword signal computed the way HW2 did, run one hypothesis test (e.g., did customers with negative-keyword reviews churn at a different rate / did campaign A outperform campaign B), and write 3–4 sentences interpreting the result in plain business language (this "explain it back" requirement is one of the more AI-resistant elements, since LLMs tend to produce generic interpretations that don't match the student's specific slice).
12. **Business ML mini-project (Wk 12)** — Pick one business problem — **churn classification**, **demand-forecasting regression**, or **customer-segmentation clustering** — train/evaluate a model on a provided dataset, compare at least two settings or model types, and write a short recommendation memo aimed at a business stakeholder, not a technical audience.
13. **Review similarity search: TF-IDF vs. embeddings + FAISS, with an LM comparison (Wk 13)** — Using a set of customer reviews (reuse/extend the HW2 corpus so the unstructured-data thread pays off), (a) clean and tokenize the text, build TF-IDF vectors, and retrieve the nearest reviews to a query with `scikit-learn`'s `NearestNeighbors`; (b) call the shared course package's `embed()` function to get dense embeddings for the same reviews, build a FAISS index, and retrieve nearest neighbors the same way; (c) run both retrievers on 2–3 personalized query reviews (e.g., a new complaint), optionally compare against directly prompting a language model via `ask_llm()` for the same task, and write a short note on which approach a support team should actually use and why — explicitly connecting back to the churn signal from HW2/HW11, and to the rule-based approaches from HW2/HW6/HW9.
14. **Final stock-price/demand forecasting simulation (Wk 14, take-home)** — A Monte Carlo simulation forecasting a **stock price** (simple random-walk or geometric-Brownian-motion style price path) or **demand under uncertainty**, directly mirroring the catalog's own example, that must reuse at least one data structure and one algorithm concept from earlier in the course, plus a semester-reflection on how AI tools changed the way they coded by the end vs. the beginning, and a short note on what a business would/could do with the simulation's output.

## 6. Verifying Understanding Without Policing AI Use

Detecting or quantifying AI use reliably isn't realistic, and trying to grade it directly ("less AI, more points") mostly just teaches students to hide it. So the plan flips the lever: ask for honest, ungraded-by-degree disclosure, and separately verify comprehension through mechanisms that work no matter how the code was produced. Concrete mechanisms woven into the plan above:

- **Honest, completion-only AI-usage logs.** A mandatory 3–5 sentence note on what AI help was used and what had to be fixed, graded pass/fail on completeness and honesty only — never scaled to how much AI was reported. A student who says "I used AI heavily for the boilerplate, then fixed X" gets the same credit as one who wrote everything unaided. This normalizes disclosure instead of driving usage underground.
- **"Explain it back" requirements.** Several assignments require a short written interpretation tied to the student's own (personalized) output — generic AI explanations don't match personalized data, so a student who can't explain their own result reveals a comprehension gap regardless of how the code was written.
- **In-class code-reading quizzes (part of the 20%).** Periodic "predict the output" or "find the bug in this snippet" quizzes, done live without notes, validate understanding directly and independently of how the homework code was produced.
- **Occasional oral walkthroughs.** A short, low-stakes "walk me through this function" spot-check (in office hours or the first few minutes of class, a few random students each week) — quick to run, and a fast, low-friction way to confirm a student can navigate and explain their own submission.
- **Per-student personalization.** Seed datasets/parameters from each student's ID so hidden tests validate against values that differ per student — this isn't about catching AI use, but adapting *any* copy-pasted answer (human or AI-sourced) to pass requires actually understanding it.
- **Require student-authored tests, not just passing code.** Grading part of the score on the tests *students* write (coverage/thoughtfulness) forces engagement with edge cases that a pasted solution doesn't automatically include.
- **A dedicated skills session (Wk 7), not just a policy.** Rather than a prohibition, teach prompting, verification against tests, and where current tools fail — research on LLM performance on programming assignments finds it varies a lot by assignment type and struggles particularly with context-specific and multi-step tasks, which is useful to build assignments around ([SIGCSE 2025](https://sigcse2025.sigcse.org/details/sigcse-ts-2025-Papers/108/Designing-LLM-Resistant-Programming-Assignments-Insights-and-Strategies-for-CS-Educa)).
- **Cumulative codebases.** Where feasible (e.g., the Wk 5 CLI tool reused/extended in Wk 6, or the final simulation reusing an earlier data structure), requiring students to build on their *own* prior code makes wholesale AI regeneration each week harder to pass off cleanly, and gives the oral-walkthrough check something continuous to probe.
- **Favor authentic, locally-grounded tasks over generic ones.** Assignments tied to a specific dataset, prior lecture, or class-specific context (rather than "write a function that reverses a string") are both more resistant to generic AI answers and better pedagogy in general ([WashU Center for Teaching and Learning](https://ctl.wustl.edu/resources/ai-resistant-assignments/)).

## 8. Open Questions Worth Deciding Before Session 1

- Whether the personalization seed comes from student ID, GitLab username, or a roster you control — determines how much setup work the CI pipeline needs.
- How strict the "no full solution from AI" policy should be for the earliest assignments (Wks 1–4) vs. later — many instructors go from "AI as tutor only" early to "AI as pair programmer with disclosure" later, matching what you're already leaning toward.
